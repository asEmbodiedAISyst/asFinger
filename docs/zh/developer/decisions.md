# 设计决策

每条先说决策，再说理由。

## 所有输出出自同一份配置

打印件、仿真模型和机器人程序，必须对 TCP 和相机的位置有一致的认识。三者各自手工维护，迟早会对不上。让一份配置成为它们共同的来源，改一个参数，所有输出一起变。

## 坐标系有名字，而且写明

工具的每个接口都是一个有名字的坐标系：法兰、安装面、TCP、手机、每个相机。输出里带着这些坐标系：MJCF 里的 site，`resolved.json` 里的条目。使用者从模型里读 TCP 偏移，不用在零件上量。

## 形状只用简单实体加并集、差集

MuJoCo 的碰撞几何用的是长方体、球和圆柱。配置用同样的形状，碰撞模型就直接来自配置，不必另写一份。这几种形状加上并集和差集，足够描述推杆，在别的软件里重建也容易。手机支架这类不简单的零件，用导入网格来处理。

## 核心是纯 Python

`geom`、`expr`、`frames`、`csg`、`options`、`interference` 和 `mjcf` 只用标准库，因此可以原样在浏览器的 Pyodide 里运行，也可以在 CAD 软件自带的 Python 解释器里运行。只有生成网格时才需要 numpy 和 manifold3d。

## 浏览器里运行同一套 Python

编辑器没有用 TypeScript 再实现一遍参数、坐标系和求解器，而是直接在 Pyodide 里运行这个包。代价是第一次打开要下载约 13 MB；好处是同一份配置在编辑器里和命令行里结果相同。只有网格这一步有两份实现（`mesh.py` 和 `csg.ts`）：浏览器直接调用 Manifold 的 WebAssembly 版本。

## 表达式按白名单计算

配置可能来自别人，也可能来自编辑器。`expr.py` 用 `ast` 解析表达式，只允许数字、名字、算术、比较、条件表达式和一组固定的函数，从不调用 `eval`。

## 求解坐标系把结果存下来

手机的位姿是求解器算出来的。配置把结果连同输入的哈希一起存下。生成时用存着的结果，过期了就警告。这样一来，求解器的代码改了，生成结果也不会变，打印过的版本可以原样重建。代价是改了参数之后要记得加 `--resolve`。编辑器是交互式的，所以每次都重新求解。

## 螺钉孔留在机械臂的坐标系里

推杆底座上的孔是在 `F_robot` 里切的，不是在推杆自己的坐标系里。改安装转角时，孔始终对着法兰的孔位，转的是孔上面的推杆。所以对同一个法兰，任意安装转角都能打印。

## 选项只裁剪，不改文件

选项从配置的一个“视图”里去掉坐标系和依赖它们的内容，文件本身什么都不丢。使用者把手机关掉再打开，数据还在；从编辑器导出的配置也总是完整的。

## 检查是配置里的数据

限制条件和干涉规则连同提示信息都写在配置里，生成器和编辑器读的是同一套规则。新的工具变体自带规则，不用改代码。

## STL 写在零件自己的坐标系里

打印件写在它自己的坐标系里，打印组写在组里第一个零件的坐标系里。对推杆来说，这样安装面正好在 z = 0，也就是贴打印床的那个面。给 MuJoCo 用的网格则写在 MJCF body 的坐标系里。

## 网站是静态的

首页、编辑器和文档都是静态文件，编辑器的计算在浏览器里完成。所以网站放在 GitHub Pages 上就能运行，不需要服务器，使用者输入的内容也不会离开浏览器。
